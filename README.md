# Dラベル スキャナ

現品票・Dラベルのバーコード / OCR 読み取りツール（完全オフライン・PWA）。

## 今のアプリが何をするか

画面は1つだけです（`src/ui/SimpleScanScreen.tsx`）。

- カメラ映像を表示しながら、バーコードを検出します。読み取りの契機は2通りから選べます（設定は端末に記憶され、既定は「常に読む」）。
  - **常に読む**: カメラを向けている間ずっと読み続けます（従来からの挙動）。棚卸しのように次々に読む作業向け。
  - **長押し中だけ**: 「押して読み取り」ボタンを押さえている間だけ読みます。現品票が密集していて、狙っていない隣のラベルまで拾ってしまう場所向け（ハンディターミナルのトリガーと同じ操作感）。
- 画面中央の枠（ROI）に対して「枠内をOCR」ボタンでシャッターを切り、その瞬間の画像を認識します。既定エンジン（ML Kit）で読めなかった・怪しいときは、撮り直さず同じ画像のまま「精密読み取り」ボタンで高精度・低速な PaddleOCR に読み直させられます（詳細は後述の「3.5」）。
- バーコードとOCRの結果は、フィールドへの振り分けや保存を行わず、**1本の一覧に時系列（新しい順）でそのまま並べるだけ**です。
- 一覧の各行はコピー・削除ができ、フッターの「全部コピー」で改行区切りの全件、「クリア」で一覧を空にできます。
- 結果は**メモリ上にのみ**保持されます。画面を閉じる/リロードすると消えます。これは意図的な仕様です（後述）。

設定の置き場所は「**設定は上、その場の操作は下**」という原則で整理してあります。

- **共通設定バー**（モード切替のすぐ下）: 一度決めたらしばらく変えない設定を、モードを問わず同じ位置に置きます。位置と中身がモード切替で動かないので、押し間違いが起きません。
  - **画質**（最大 / 標準 / 軽量）: カメラの取得解像度。バーコードのバーの細さにもOCRの精度にも直接効くため共通設定です。
  - **整形**: 読み取った値から不要な部分を取り除くルール（後述）。**バーコードとOCRで1つのルールを共有**します。
- **バーコードモード固有**: 「枠内のみ」「読み取り音」「読み取り契機」「誤読ガードを設定」。いずれもバーコードの読み取り挙動そのものを変える設定で、OCRには関係しません。誤読ガードは設定項目が多いため専用パネルに切り出してあります（後述の「バーコードの誤読ガード」）。
- **文字（OCR）モード固有**: **エンジン**（ML Kit / PaddleOCR）。バーコードモードの「読み取り契機」と対になる位置に置いてあり、**シャッターを押す前から常に見えます**。OCR専用の設定なので共通設定バーには置きません（詳細は後述の「3.5」）。
- **OCR結果カード**: **抽出フィルタ**（フィルタなし / 数字のみ / 英数字のみ / 数字として解釈）。認識済みテキストに対する後処理で、切り替えるたび即座に反映されます。加えて、撮り直さず**今表示している同じ静止画のまま**より高精度・低速な PaddleOCR で読み直す「**精密読み取り**」ボタン（ML Kit で読んだ結果のときだけ表示）も置いています（詳細は後述の「3.5」）。

### 読み取り値の整形（バーコード・OCR共通）

共通設定バーの「整形」から、読み取った値の不要な部分を取り除くルールを設定できます。**バーコードとOCRで同じルールを共有**します（設定が2箇所に増えると現場が混乱するため）。

- 指定した文字列が最初に現れた位置までを捨てる / 以降をすべて捨てる（スペースやGS区切りに便利）
- 前方一致する接頭辞・後方一致する接尾辞を取り除く（複数指定可）
- 前後の空白を除去する

整形ルールは**読み取った瞬間に確定**します。後からルールを変えても、既に一覧にある行には遡って効きません（バーコード・OCRとも同じ心的モデルです）。

OCRでの合成順序は **手直し（タップで `1↔I` 等を切り替え）→ 整形 → 抽出フィルタ** です。整形をフィルタより先に行うのは、フィルタが先に空白や区切り記号を消してしまうと、整形が探す区切り文字自体が失われて機能しなくなるためです。

いずれの場合も、**エンジンの生の読み取り結果は常に別行で見せ続けます**（整形や補正で何が起きたか分からなくならないように）。

### 「枠内のみ」をOFFにしたとき

バーコードモードで「枠内のみ」をOFFにすると読み取り対象は画面全体になります。このとき**水色の枠と、枠外を暗くする効果は表示しません**。画面全体が対象なのに枠外が暗いままだと、意味と見た目が矛盾して紛らわしいためです。「読み取り済み」の通知はプレビュー領域の中央に出ます。文字（OCR）モードの枠は常に「OCRの対象そのもの」なので、常に表示されます。

OCRエンジンの既定は [Google ML Kit Text Recognition v2](https://developers.google.com/ml-kit/vision/text-recognition/v2)（端末内蔵モデル）です。Capacitorのネイティブプラグイン経由でしか動かないため、**既定のままではAndroidアプリ（APK）版でのみ使えます**。ただし読めなかったときの高精度・低速フォールバックとして PaddleOCR（WASM）を追加してあり（詳細は後述の「3.5」）、ブラウザ（`pnpm dev` / GitHub Pages）ではこちらに自動で切り替わるため、**文字モード自体はブラウザでも使えます**（バーコードモードはこれまで通りブラウザでも使えます）。

## なぜこんなに機能が少ないのか

もともとこのアプリには、ラベル定義エディタ・スキャン履歴・CSV書き出し・設定画面・フィールド単位の組み立てといった機能一式がありました。しかし、現場（倉庫・工場フロア）の具体的な要件がまだ固まっていない段階でこれらを作り込んでしまい、UIが煩雑になっていました。

そこで、まずは最小限の「読み取るだけ」のツールを現場に持って行き、実際に何が必要かを確認する方針に変更しました。

- **画面は1つだけ**（タブなし・履歴なし・CSV書き出しなし・プロファイル編集なし・設定画面なし）
- **永続化なし**（結果はメモリ上のみ。意図的な仕様）

## 退避済みの機能（削除ではない）

要件が固まったら再配線する前提で、コードは削除せずに残してあります。

- `src/ui/legacy/` — 旧来の画面一式（`ScanScreen.tsx` / `RecordSheet.tsx` / `RawDataPanel.tsx` / `HistoryScreen.tsx` / `ExportScreen.tsx` / `ProfileListScreen.tsx` / `ProfileEditor.tsx` / `FieldRuleEditor.tsx` / `TestPad.tsx` / `SettingsScreen.tsx`）。どの画面からも呼ばれていませんが、型チェックは通る状態を維持しています。
- `src/parse/` — バーコード/OCR結果をラベル定義（プロファイル）に従ってフィールドへ変換するパース・バリデーションエンジン。
- `src/store/` — IndexedDB（プロファイル・履歴・設定・下書き）まわりの永続化コード一式。
- `src/export/` — CSV書き出し。

これらは `src/ui/legacy/` の画面から参照されており、現在のアプリの実行パスからは呼ばれていませんが、`tsc -b` の型チェック対象には含まれています。

## OCR まわりの修正履歴

### 1. 「数字が認識されない」（初期の修正）

原因は2つありました。

1. `tessedit_char_whitelist`（文字ホワイトリスト）を設定していたこと。LSTMエンジン（本アプリの既定）ではこのパラメータの指定が不安定で、文字がまるごと脱落する既知の原因になるため、エンジンへの指定自体をやめました。絞り込みが必要な場合は、認識後のテキストに対して JS側でフィルタをかける方式（`src/scan/ocr/postprocess.ts`）に置き換えています。
2. 認識前に自前で大津の二値化（Otsu binarization）を行っていたこと。Tesseract は内部で自前の適応的二値化を行うため、事前にハード二値化した画像より素のグレースケール画像の方が概して精度が良く、特にROI帯にバーコードのバーが写り込むケースでは二値化がバーを大きな黒い塊にしてしまい有害でした。二値化は削除し、グレースケール化とスケーリングのみを残しています。

### 2. APK版で OCR がまるごと使えなかった（`.gz` の展開）

学習データを `eng.traineddata.gz` として同梱し、tesseract.js の `gzip: true` で「fetch した先頭バイトが gzip マジックバイトなら zlibjs（純JS）で展開する」方式を使っていました。しかし `.gz` を HTTP 相当の経路で運ぶと、受け取るバイト列が「gzip のまま」か「途中の層で展開済み」かは `Content-Encoding` の付与に依存して一意に決まりません。とくに APK 版では Capacitor の `WebViewLocalServer` が MIME を `URLConnection.guessContentTypeFromName()` 任せで返すうえ、`aapt` が APK 内で `.gz` をもう一度 deflate 圧縮するため **二重圧縮**の状態で配信されていました。

対処として **学習データを非圧縮の `eng.traineddata` として同梱し、`gzip: false` を渡す**ようにし、展開経路そのものを無くしました。`aapt` はどのみちアセットを deflate するため、APK のサイズはほとんど変わりません。詳細は [`docs/apk.md`](docs/apk.md) の「10. OCRエンジンについて」を参照してください。

あわせて、この失敗が `handleWarmup` の `catch {}` で完全に握りつぶされていた（＝「OCRモードには入れるのに認識だけが動かない」という気付きにくい壊れ方をしていた）問題も直しました。`preloadOcr` は失敗しても reject せず `{ ok: false, error }` を返し、画面側がその内容を通知として表示します。

### 3. OCRエンジンを2つに（Tesseract / ML Kit）→ 実機比較の末に ML Kit へ一本化

現場から「**バーコード自体がかすれていることも少なくない**」という報告があり、OCRを補助ではなく主機能として強化する必要が出ました。あわせて「社内スマホからGitHub Pagesへアクセスする形にはならない」＝**APK一本化でよい**という判断が出たため、Androidネイティブの選択肢が取れるようになりました。

そこで [Google ML Kit Text Recognition v2](https://developers.google.com/ml-kit/vision/text-recognition/v2)（端末内蔵モデル）を**2つ目のOCRエンジン**として追加し、tesseract.js と併存させていました。

| | tesseract.js（当時） | ML Kit |
| --- | --- | --- |
| 動作環境 | ブラウザ・APK 両方 | **APKのみ**（Capacitorのネイティブプラグイン） |
| 得意分野 | スキャンした書類 | **カメラで撮った写真** |
| 文字ごとの信頼度 | 返す | **返さない** |
| `pnpm dev` での検証 | できる | **できない** |

**なぜ一時的に両方残していたか**: 当時は精度を測る手段が無く、どちらが現場のラベルで実際に読めるか分かっていなかったためです。推論だけでエンジンを入れ替えると、良くなったのか悪くなったのか誰にも分かりません。そこで比較モード（後述）を作り、実物のラベルに両方をかけて**決着してから負けたほうを消す**方針にしていました。

**結果**: 実機での比較の結果、**ML Kit が圧倒的に高精度**でした。バーコードの除去（自動マスク）もML Kit側でうまく機能しています。加えて配布形態も APK 一本化に決まったため、`pnpm dev` でしか検証できないという tesseract.js の利点（ブラウザで動く）も意味を失いました。**そのため tesseract.js は完全に削除し、現在はML Kitのみを使っています。**

注意点は今も変わりません。

- **ML Kitは信頼度を返しません。** `OcrResult.confidence` には常に `0` が入りますが、これは「信頼度ゼロ」ではなく「**信頼度という情報が無い**」という意味です。UI側では信頼度表示を出さず、結果カードには代わりに「ML Kitは信頼度を返しません」という注記だけを表示します。
- **ML Kitには前処理を通していない素の画像を渡すのが既定です。** 前処理パイプライン（グレースケール化・コントラスト正規化・罫線除去・文字高96px基準への縮小）はTesseractのLSTM向けに調整したもので、自然な写真で学習されたML Kitには不利にしか働きません。前処理パイプライン自体は比較材料として残してあり、比較モードで実際に効果があると分かった組み合わせを採用することもできます。

### 3.5. 読めないとき用に PaddleOCR を追加（高精度・低速）

ML Kit で実用水準に達したものの、現場から「**1つだけだと不安が残る。読み取れないとき用の手段が欲しい**」という要望が出ました。そこで PaddleOCR（PP-OCRv5 mobile）を [onnxruntime-web](https://onnxruntime.ai/) で動かす2つ目のエンジンとして追加しています。

| | ML Kit（既定） | PaddleOCR |
| --- | --- | --- |
| 速度 | 速い（数十〜百数十ms） | **遅い**（数百ms〜数秒。WASM単一スレッド） |
| 動作環境 | **APKのみ** | ブラウザでも動く |
| 初回の準備 | 不要（端末内蔵） | **約35MBの読み込み** |
| 信頼度 | 返さない（常に0） | **本物の値**（CTCの確率から算出） |

**UIでの見せ方**: 2つの導線を使い分けています。

- **撮る前に選ぶ「エンジン」設定**: 文字モードのシャッターのすぐ上、バーコードモードの「読み取り契機」と対になる位置に、常時見えるエンジン選択（ML Kit / PaddleOCR）があります。既定は引き続き ML Kit ですが、**「毎回 PaddleOCR で読みたい」場合は撮る前に選んでおけます**。以前はこの選択が結果カードの中（＝一度読み取りに成功しないと出てこない場所）にしかなく、「ML Kit で読む前に PaddleOCR を選んでおく」ことができませんでした。同じ設定を2箇所に置くと現場が混乱するため、結果カード側にあった同じ Select は削除しています。
- **読めなかった直後にその場で押す「精密読み取り」ボタン**: 主役はこちらのままです。同じ静止画を PaddleOCR で読み直すだけなので撮り直しは不要です。「設定を開いてエンジンを切り替えてもう一度撮る」は現場には手順が多すぎる、という判断は変わっていません。

**副作用として Web 版で文字モードが復活しました。** PaddleOCR は WASM で動くためブラウザでも動作します。ML Kit 一本だった間は「OCRの変更を確認するには毎回APKを焼いて実機に入れる」しかありませんでしたが、PaddleOCR 経路については `pnpm dev` でローカル検証できます。

**同梱物**（`public/vendor/`、合計約35MB。Service Worker の precache からは除外し、初回利用時にだけ取得します。この前提が実際には破れていたことがあり、経緯は次節「3.6」を参照）

- `paddleocr/ppocrv5-mobile-det.onnx`（4.7MB、文字領域の検出）
- `paddleocr/ppocrv5-mobile-rec.onnx`（16.5MB、文字認識）
- `paddleocr/ppocrv5_dict.txt`（18383行の文字辞書）
- `onnxruntime/ort-wasm-simd-threaded.wasm`（14MB）＋ その JS グルー

**実装上の割り切り**（コード内のコメントにも記載）

- 検出の後処理で、本家が使う「最小面積の**回転**矩形」ではなく**軸平行の矩形**を使っています。このアプリは利用者が枠で囲って撮るためテキストがほぼ水平で、回転矩形には凸包＋回転キャリパスが要りコード量とリスクに見合わないためです。**大きく傾いた文字は苦手**という制約が付きます。
- unclip（箱の拡張）も Vatti クリッピングではなく「面積 × 比率 / 周長」の近似です。
- スレッド並列は使いません（`numThreads = 1`）。マルチスレッドには COOP/COEP ヘッダが必要ですが、Capacitor の WebView 配信では設定できないためです。

**モデルの出所について**: PaddleOCR 公式が配布しているのは Paddle 推論形式（`.pdiparams`）で ONNX ではないため、変換済みのものを使っています。入手元はライセンスこそ上流と整合（Apache-2.0）していますが、**取得時点でダウンロード数0の個人アカウント**でした。ONNX はデータ形式で実行コードが混入する性質のものではなく、`onnxruntime-node` で実際にロード・推論して健全性を確認していますが、広く使われている配布元ではない点は把握しておいてください（`scripts/smoke-paddle.mjs` に検証手順と結果を残してあります）。

### 3.6. precache への14MBの二重同梱事故（onnxruntime-web のフォールバック経路）

「35MBは初回利用時にだけ取得する」と上で説明していますが、実際のビルド成果物ではこの約束が一時期破れていました。ここでは何が起きていたか・なぜ気付きにくかったか・どう塞いだかを記録します。

**何が起きていたか**: `onnxruntime-web` パッケージ内には、`wasmPaths` が未設定のときのフォールバックとして `new URL("ort-wasm-simd-threaded.wasm", import.meta.url)` という記述があります。Vite はこれを**静的なアセット参照**として解釈し、`public/vendor/onnxruntime/` に置いてある14MBのwasmと**中身がまったく同じファイル**を `dist/assets/ort-wasm-simd-threaded-<hash>.wasm` としてもう1部生成していました。`dist/assets/` 配下は `workbox.globIgnores: ['**/vendor/**']` に一致しないうえ、`globPatterns` の `'wasm'` には一致するため、**この14MBが Service Worker の precache に静かに紛れ込んでいました**。同じ重複は `PACKAGED=1`（APK版）のビルドにも入っていたため、**APK自体も14MB余計に太っていました**（詳細は [`docs/apk.md`](docs/apk.md) の「APK サイズについて」を参照）。

**なぜ気付きにくかったか**: `src/scan/ocr/paddle/session.ts` は起動時に必ず `ort.env.wasm.wasmPaths` を設定するため、このフォールバック経路は**実行時には決して通りません**。つまり動作上は何の異常も起きず、アプリを触っている限り一切表面化しない、純粋な死重でした。加えて、従来のCIゲートは「precacheのマニフェスト文字列に `vendor` という単語が含まれるか」しか見ておらず、`dist/vendor/` を経由しないこの `dist/assets/` 側の混入は検出対象外でした。

**どう塞いだか**: `vite.config.ts` に `patchOnnxruntimeWasmUrlPlugin` を追加し、onnxruntime-web の該当箇所の `import.meta.url` を使わない等価な式へビルド時に書き換え、Vite のアセット解決の対象から外しました。置換パターンが1件も当たらなければビルド自体を失敗させています（onnxruntime-web の将来のバージョンアップでこの記述が変わり、対策が静かに無効化されて事故が復活する事態を防ぐためです）。

**CIゲートの強化**: 従来のゲート（precacheのマニフェスト文字列に `vendor` が含まれないことだけを見る）ではこの事故を検出できなかったため、`dist/sw.js` の precache を実際にパースし、次の3点で落とすように強化しました。同じ内容を `.github/workflows/ci.yml` と `gitlab/ci/build.yml` の両方に置いています（このリポジトリは GitHub Actions と GitLab CI に同じ内容を用意する方針のため）。

1. precache に `dist/vendor` 配下のパスが含まれないこと（従来通り）
2. precache に `ort-wasm` 系のファイル名が含まれないこと（今回の実際の事故を直接検出するための追加）
3. precache の合計サイズが**5MB超**にならないこと（経路によらない保険）

**実測**: 修正前は precache が **23エントリ・15,307 KiB** あり、うち14MB分がこの重複でした。修正後は **22エントリ・1,678 KiB** です。`dist/vendor/` 配下の5ファイル（onnxruntime の `.mjs` と `.wasm`、PaddleOCR の検出・認識モデルと辞書）は従来通り precache の対象外のまま残っており、必要になったときにだけ取得されます。

### 4. 精度を測れるようにした（比較モード）

**このリポジトリには精度を測る手段が一切ありませんでした。** 実物の画像もゴールデンデータも無く、ここまでの改善はすべて推論ベースで、良くなったのか分からないまま重ねられていました。現場の実画像は社外に出せない事情があるため、リポジトリに置く代わりに**アプリ内に比較機能**を持たせています。

文字モードの結果カードの「設定を比較」から開くと、**シャッターで撮った同じ静止画**に対して複数の設定を一括で走らせ、結果を並べて比較できます（再撮影はしません）。エンジンが ML Kit の1つだけだった間、比較軸は**前処理の組み合わせ**のみでした（tesseract.js があった頃はここにPSM・エンジンの軸も含んでいましたが、削除に伴って無くなりました）。PaddleOCR を追加した後も、**比較軸は引き続き前処理の組み合わせだけ**で、1回の比較は常に単一エンジンで走ります（「今回の比較はどのエンジンで走っているか」まで軸にすると、食い違いが前処理由来なのかエンジン由来なのか切り分けられなくなるためです）。パネルには「今回の比較は ML Kit / PaddleOCR で実行します」という帯を常時表示し、PaddleOCR のときは所要時間（1件ごとに数百ms〜数秒。ML Kitより明確に時間がかかります）を事前に案内します。

- 「素の画像（前処理なし）」対「前処理すべてON」、および「罫線除去だけON」「縞マスクだけON」など、**どの前処理が効いているかを切り分ける**プリセットを用意
- 各結果に**実際にエンジンへ渡した画像のサムネイル**を表示（何が効いたのかが目で見える）。PaddleOCR で走らせているときは、各結果に信頼度の実数値（CTC由来）も表示します。
- 「この設定を使う」で採用・永続化されるのは**前処理設定だけ**です。エンジンはこの操作では変わりません（比較に使ったエンジンは、この画面を開いた時点の既定エンジンのままです）。

**正解が分かるのは人間だけ**なので、現場で実物のラベルを撮って目で見て選んでもらう前提の道具です。次の予定は「前処理を変えた2パス」（素の画像 vs コントラスト補正）で結果の食い違いを可視化すること（`src/scan/ocr/agreement.ts` の `compareOcrPasses` / `mergeVerdicts` はこのために残してあります）。

### 5. APK化後に精度が落ちて見えた（スケール決定ロジック）

`computeOcrScale` が **入力ROIの画素数だけ**から倍率を決めており、実際の文字の大きさを見ていませんでした。そのため同じ物理的な大きさの文字でも、カメラの解像度が高いほど強く縮小されるという、直感と正反対の挙動になっていました。

| 検証環境 | ROI の実サイズ | 旧: 倍率 | 新: 倍率 → 出力 |
| --- | --- | --- | --- |
| PCブラウザ 1280×720 | 1024×130 px | **2.0（拡大）** | 0.74 → 756×96 |
| 実機 12MP 相当 | 3072×389 px | **0.6（縮小）** | 0.25 → 758×96 |

「PCでは拡大され、実機では縮小される」ことが体感の主因でした。現在は **出力の高さ**（`TARGET_ROI_HEIGHT_PX = 96`）を基準に倍率を決め、そのうえで画素数予算（`OCR_PIXEL_BUDGET`）を超えるときだけ追加で縮小する2段構えにしています。撮影解像度によらず同じ大きさの文字はほぼ同じ出力サイズになります。

同時に次の2点も改善しました。

- 拡大時の補間を**ニアレストネイバーから双線形補間へ**変更（文字のエッジがブロック状にジャギーになるのを解消）。縮小側のボックスフィルタは従来通り。
- グレースケール化の後に**パーセンタイル方式のコントラスト正規化**（下位/上位2%を 0..255 へ線形ストレッチ）を追加。倉庫・工場の照明ムラに強くなります。線形変換のみでしきい値判定は行わないため、「二値化はしない」という上記1の方針とは矛盾しません（レンジが極端に狭い場合はノイズ増幅を避けるため何もしません）。

### 6. 枠線・バーコードの映り込みと「I と 1」への対策

現場から挙がった3つの弱点への対策です。

**枠線（罫線）**: 現品票は表形式で、ROIに罫線が入ると文字と接触してLSTMが崩れます。`src/scan/ocr/lines.ts` で、行・列ごとに**最長の連続暗画素ラン**を測り（縞を数える `countTransitions` では罫線は捕まりません。罫線は逆に反転が少ない）、ROI幅の一定割合を超えたら罫線と判定します。除去はベタ塗りではなく**1次元の線形インペイント**で、交差した文字のストロークを残します。検出できた場合は罫線の内側へROIを自動で詰めます（消すより避けるほうが安全）。

**バーコードの映り込み**: 従来の `trimBarcodeBoxesToStripes` は**デコードできたバーコードの枠の内側しか見ていません**でした。ROIの端で切れてデコードできないバーコードは素通りします。これが取りこぼしの主因でした。`stripes.ts` に ROI **全体**を走査する `detectStripeRegion` を追加し、デコード可否と無関係に縞を検出できるようにしました。行・列の両方で密な矩形は2Dシンボル（QR/DataMatrix）として扱います。

**I と 1**: 3層で攻めています。

1. **辞書を切る（tesseract.js 時代のみ）**: 品番・数量は英単語ではないので、tesseract.js 内蔵の英語辞書による補正は誤爆の原因にしかなりません。`load_system_dawg` 等を `0` にして無効化していました。tesseract.js を削除した現在の ML Kit には辞書補正の概念自体が無いため、この対策は過去のものです。
2. **混同補正**（`correctDigitConfusions`）: 読み取り対象が「ほぼ数字、一部に `-` と `+`」と確定しているため、`I l | ! i → 1`、`O o D Q → 0`、`S s → 5` … の決定論的な置換を安全にかけられます。NFKC正規化で全角も半角化。エンジンに依存しない後処理（`src/scan/ocr/postprocess.ts`）なので ML Kit でもそのまま使えます。
3. **紛らわしい文字の手直し ← 本命**: 自動補正は必ずどこかで外れます。「機械が迷った箇所を人が一瞬で直せる」導線のほうが、実用精度としては効きます。以前は文字ごとの信頼度（tesseract.js が返していた）と2パス照合（`agreement.ts`、LCSで対応付けるので片方が1文字多く読んでも以降が全部ずれない）の両方で「怪しい文字」を自動判定し、その文字だけをタップ可能にしていました。**ML Kit は信頼度を一切返さない**ため、この自動判定は成立しなくなりました。そこで方針を「機械が怪しいと言った文字だけ直せる」から「**紛らわしい字形の対応表に載っている文字はすべてタップ可能**」に変更しています。**タップで `1↔I`、`0↔O`、`5↔S` などを手で切り替え**られ、修正結果はコピー・一覧に反映され、エンジンの生テキストは常に別行で見え続けます。`agreement.ts` の `compareOcrPasses` / `mergeVerdicts`（2パス照合部分）はエンジンに依存しないため引き続き残してあり、「前処理を変えた2パス」として作り直す予定です。

### 7. PaddleOCRが必ず「文字を読み取れませんでした」になっていた（検出のスコア判定の順序）

**PaddleOCR経路が実質的に一度も機能していなかった不具合です。** `src/scan/ocr/paddle/boxes.ts` の `postprocessDetection`（DBNet検出の後処理）が、箱のスコアを **unclip（箱を外側へ拡張する処理）の「後」の矩形に対して計算していました**。本家PaddleOCRの `box_score_fast` は、拡張前の（tightな）輪郭領域に対して確率平均を出し `box_thresh` と比較したうえで、通過した箱だけをunclipします。この順序が逆になっていました。

**なぜこれが「精度が落ちる」程度で済まず致命的だったか**: `unclipBox` は `distance = 面積 × unclipRatio / 周長` だけ各辺を外側に広げるため、`unclipRatio=1.5`（既定値）のとき拡張後の面積は元の面積のおよそ2.5〜3倍になります。仮に元の箱の内部が確率1.0で完全に埋まっていたとしても、拡張後の矩形全体で平均を取れば「元の面積 / 拡張後の面積」でせいぜい0.33〜0.40（正方形に近いほど0.33、極端に細長いほど0.40に漸近するが、これを超えることは原理的にありません）にしかなりません。ところが `DEFAULT_BOX_THRESHOLD` は **0.6** です。つまり画像に何が写っていようと全部の箱が閾値未満で除外され、`detectTextBoxes` は常に空配列、`recognizeWithPaddle` は常に空文字を返し、UIは毎回「文字を読み取れませんでした」を表示していました（内部確率0.95・外部0.02という理想的な確率マップですら、240x26/120x20/400x40/60x16のどの矩形サイズでもunclip後スコアは0.34〜0.37に留まり、0.6を一度も超えませんでした）。

**なぜ純粋関数のユニットテストが全部緑だったのに気付けなかったか**: `src/scan/ocr/paddle/__tests__/boxes.test.ts` の `postprocessDetection` のテストは、すべて `{ boxThreshold: 0.2 }` を明示的に渡して閾値を下げたうえで検証しており、しかも期待値のコメント自体が「拡張後の面積で割った値」を正解としてハードコードしていました。**既定値（0.6）を通す経路が一度もテストされておらず、テストが不具合をそのまま追認していた**のです。修正にあわせて、スコアリングをtight（拡張前）の箱に対して行うよう順序を直し、`boxes.test.ts` に **既定オプションのまま**現実的な確率マップ（240x26の塊、内部0.95・外部0.02）で1箱検出できることを確認する回帰テストと、極端な縦横比（正方形に近い箱・細長い箱）でも既定値で通過することを確認するテストを追加しました。

**実物のモデルを通した end-to-end の検証手段が無かった問題も合わせて塞ぎました**: 上記のとおり、純粋関数のテストがいくら緑でも「実物のONNXモデルを通した経路が一度も動いたことがない」まま気付けない、という穴がありました。`src/scan/ocr/paddle/__tests__/e2e-real-model.test.ts` を追加し、5x7の簡易ビットマップフォントで自前生成した合成画像（「1234567890」を大きく描画）を、検出→後処理→切り出し→認識→CTCデコードの実物の経路（後処理・CTCデコードは `src/scan/ocr/paddle/` の実装をそのまま呼び出し、再実装しない）に通して検証できるようにしています。`onnxruntime-node` を一時的に入れて実行する必要があるため（本体の依存には含めない）、`pnpm add -D onnxruntime-node` した環境でだけ実行され、無い環境（＝通常の `pnpm test`）では自動でskipされます。実行方法・実測結果はファイル冒頭のコメントに記録してあります。

## バーコードの誤読ガード

現場から「バーコードが切れているなどの際に、まったく違う値が入ることがままある」という報告がありました。ITF（Interleaved 2 of 5）やCode39のように、部分的に読めてしまうと「短いが規格上は妥当な別の値」がデコードされてしまう症状です。これに対処するため、デコード後の結果を検証する4種類のガードを追加しました（`src/scan/barcode/guards.ts` / `src/scan/barcode/agreement.ts`）。バーコードモードの「誤読対策」→「誤読ガードを設定」から設定できます。

### なぜ「デコード後の検証層」が本命なのか

このアプリのバーコード読み取りには2つの経路があります。

- `src/scan/barcode/native.ts`（Android のネイティブ `BarcodeDetector`）＝ **APK版で実際に使われる主経路**。`formats`（対応させるシンボロジーの一覧）以外の内部挙動は一切設定できません。
- `src/scan/barcode/zxing.worker.ts`（zxing-wasm）＝ `BarcodeDetector` 非対応環境向けのフォールバック。

主経路（ネイティブ）は内部の検証ロジックを一切設定できないため、**両経路に共通して効かせられる唯一の場所は、デコードが終わった後の結果を検証する層**です。`evaluateBarcodeHit()`（guards.ts）がこの層で、native / zxing どちらの経路が返した `BarcodeHit` にも同じ検証をかけます。zxing側にも `validateOptionalChecksum: true` を追加していますが（zxing-wasmの既定はfalse）、これはあくまでフォールバック経路だけに効く保険であり、APK版の主経路には効きません。

### 採用した4つのガード

1. **チェックディジット（数学的検算）**: GTIN の mod-10（EAN-13・EAN-8・UPC-A・UPC-E・ITF）と Code39 の mod-43（既定OFF）。
   - **ITFはGTIN-14（14桁）のときだけ検算します。** ITFは6桁〜16桁程度まで幅広い運用がある可変長シンボロジーで、チェックディジットの有無は運用依存です。唯一の例外がITF-14（物流の集合包装コードとして広く使われる14桁の運用）で、これはGS1の規格上必ずチェックディジットを持ちます。部分読みが最も起きやすいシンボロジーでありながら、ネイティブ経路も zxing の既定もチェックディジットを検証していないため、この14桁のケースだけは検証する価値が高い一方、14桁以外まで検証対象にすると、チェックディジットを持たない正当な運用の値を誤って全て拒否してしまいます。
   - Code39のチェックディジットは規格上「任意」で、付けていない運用の方が多いため既定はOFFです。
   - Code128はmod-103のチェックディジットがシンボロジー自体に内蔵されており、どのデコーダも必ず検証済みのため何もしません。
2. **見切れ検出**: 検出枠（`box`）が解析対象画像の縁に接していたら「見切れている」とみなして棄却します（既定は各辺1%の余裕）。クワイエットゾーンやスタート/ストップキャラクタの検査はデコーダ内部の責務で後段からは検査できませんが、検出枠が画像の縁ぎりぎりにあることを見切れの代理指標として使えます。「枠内のみ」ONで検出をクロップ画像に対して行った場合、これは「水色の枠から見切れている」ことと一致します。
3. **桁数の範囲**: 受け入れる値の長さの下限・上限（既定は無制限）。部分読みは本来より短い値になることが多いため、下限が効きます。
4. **複数回一致**: 同じ値を連続N回デコードできて初めて採用します（既定2回、1回で無効化）。10fpsのループなのでN=2でも遅延は約100msです。
   - **複数のバーコードが同時に画角に写っていても、値ごとに独立してカウントします。** 「直前のフレームと同じ値か」のような単純な前後比較で数えると、2本のバーコードが交互にデコードされただけで両方とも永遠に採用されなくなってしまうためです（`agreement.ts` の `createBarcodeAgreementTracker`、値をキーにしたMapで管理）。
   - **同一フレーム内に同じ値が複数回写っていても1回としか数えません。** 同じラベルが2枚並んで写っている場合、1フレームの検出結果に同じ値が複数件含まれることがありますが、これを複数回として数えるとガードがその場で無条件に成立してしまい、何の防御にもなりません。
   - この仕組みは「一度きりのランダムな誤読」には効きますが、**切れたバーコードを毎フレーム同じように誤読する系統的な誤読には効きません**（どのフレームでも同じ値が出るため）。系統的な誤読を止めるのはチェックディジットと見切れ検出の役割で、複数回一致はそれらを補う運用的な保険です。

これらのガード（見切れ・複数回一致・桁数）は**1次元（リニア）シンボロジーにだけ適用**し、QR・DataMatrix・PDF417（2次元シンボル）には適用しません。2次元シンボルは強力な誤り訂正符号を内蔵しており、デコードが成功した時点で内容が数学的に保証されているためです（QRが枠の縁に触れていても、正しく読めていれば正しい）。

有効にするシンボロジー自体も絞り込めます。デコーダ側の `formats` を絞る方式ではなく、**デコード後に許可リストで弾く方式**を採用しています。native.tsとzxing.worker.tsそれぞれで別々にformatsを絞ると実装が2箇所に分かれるため、共通の許可リストで弾けば両経路で同じ挙動になり実装は1箇所で済みます。

### 採用しなかったもの

- **スティッチング**（レーザースキャナが長いシンボルを複数回の走査に分けて読む技法）: カメラ方式は1フレームでシンボル全体を1枚の画像として撮っており、切れているシンボルは「どのフレームでも同じように切れている」ため、継ぎ合わせるべき断片がそもそも存在せず、このアプリでは意味を持ちません。
- **クワイエットゾーン / スタート・ストップキャラクタの自前検査**: デコーダ内部（バーの間隔・パターンの解釈）の責務であり、デコード結果（文字列と正規化座標）だけを見る検証層からは検査できません。

## データ量の多い QR コードで固まる問題への対策

「データ量の多い QR を読むと落ちる」という報告について、実機が手元に無いため再現はできていません。そのかわり、**大きなシンボルを読んだときに通る経路のうち、無制限・無防備だった箇所をすべて塞ぐ**方針で調査・対処しました。以下はコードを読んで実在を確認した欠陥です。

### 1. zxing リーダーの Promise が永久に解決されない経路があった（最有力）

`createZxingReader()` の `detect()` には reject する経路が一つも無く、ワーカーの `error` / `messageerror` も購読しておらず、タイムアウトも無く、`close()` は待機中の Promise を解決しないまま `terminate()` していました。

これが `useBarcodeScanner` の `busyRef` と組み合わさると致命的でした。`detect()` の Promise が永久に未解決だと `.finally` が走らず、**`busyRef.current` が `true` に固定され、以後すべてのフレームがスキップされます**。カメラ映像は流れ続けるのにバーコードだけ一切読めなくなる ＝ 現場からは「落ちた・固まった」に見えます。データ量の多い QR は wasm ヒープを最も使う最重量ケースであり、この経路に落ちる確率が最も高いと考えられます。

対処:

- `detect()` が**必ず有限時間で settle** するようにした（1リクエスト4秒でタイムアウト → 空配列で解決）。
- ワーカーの `error` / `messageerror` を購読し、待機中の Promise を全部解決してから死亡扱いにする。
- `close()` は待機中の Promise を解決してから `terminate()` する。
- **ワーカーの自己回復**: 死亡していたら次の `detect()` で作り直す（上限3回）。上限に達したら画面に「自動復旧を諦めました。アプリを再読み込みしてください」というバナーを出し続ける。
- `useBarcodeScanner` 側に **`busyRef` のウォッチドッグ**（8秒）を追加。zxing の内部タイムアウトが効かない経路（ネイティブ `BarcodeDetector` 自体のハング等）に対する最後の安全網です。

### 2. ワーカーが返すエラーを完全に無視していた

`zxing.worker.ts` は失敗時に `error` を載せて返していましたが、受け手が `hits` しか見ておらず、毎フレーム失敗し続けても UI には「何も見つからない」としか映りませんでした。現在は連続20回（10fps で約2秒）の失敗を「持続的な失敗」とみなして自己回復をトリガーし、利用者にも通知します。

### 3. シャッター押下時の検出だけがダウンスケール保護を経由していなかった

`detectBoxes()`（OCR時のバーコードマスク検出）は、フレームループの `CROP_PIXEL_BUDGET_PX`（約2.5MP）や `ZXING_LONG_EDGE_PX`（長辺1280px）を一切通らず、映像の実解像度（画質「最大」なら 3840×2160＝約830万px、実機の12MPセンサーならそれ以上）をそのままワーカーへ渡していました。ワーカー側に最終防衛ライン（`MAX_INPUT_PIXELS = 12,000,000`）を設け、超える入力はデコードせず空配列を返します。

### 4. 読み取り値の長さが表示側で無制限だった

QR は最大 2,953 バイト / 4,296 文字を持てます。数KBの連続した1トークンを `<pre class="break-all">` に描画すると Chromium のレイアウトはかなり重くなり、一覧はスキャンのたびに全体が再レンダーされます。

**値そのものは一切切り詰めていません**（現品票の情報が欠落するのは業務上致命的なため）。一覧の表示だけを300文字までにし、行ごとの「全〇〇文字を表示」で展開できるようにしました。コピー・全部コピーで使われるのは常に完全な値です。

また、1フレームあたりのシンボル数上限（`maxNumberOfSymbols: 16`、zxing-wasm の既定は255）も設定しました。

## ライセンス情報の同梱

このアプリは完全オフライン・端末内完結（APK版は `INTERNET` 権限すら持たない）が前提のため、利用しているオープンソースソフトウェアのライセンス表記も**外部サイトへのリンクではなく、ビルド成果物に同梱**しています。アプリ内の「使い方」パネル末尾の「ライセンス情報を見る」から、通信できない場所でもそのまま閲覧できます。

一覧は `scripts/generate-licenses.mjs` が本番依存ツリー（推移的依存を含む）から自動生成し、`src/licenses/generated.ts` としてリポジトリにコミットしています。Android のネイティブ依存として組み込まれる ML Kit、zxing-wasm が内部に同梱する zxing-cpp の wasm、`public/vendor/paddleocr/` に手動配置している PaddleOCR のモデル・辞書は、いずれも npm の依存ツリーには現れないため、スクリプト内の手書きエントリで補っています。

```bash
pnpm run licenses        # 再生成（依存を追加・更新したとき）
pnpm run licenses:check  # 生成物が最新かどうかの検証（CI の verify で実行）
```

詳細は [`docs/licenses.md`](docs/licenses.md) を参照してください。

## 動かし方

```bash
pnpm install
pnpm dev        # 開発サーバー
pnpm build      # 型チェック + 本番ビルド（dist/ に出力）
pnpm preview    # ビルド済みアプリをローカルで確認
pnpm test       # vitest によるユニットテスト
pnpm lint       # oxlint
```

カメラ・バーコード検出は HTTPS（または localhost）が必要です。**OCR（文字モード）の既定エンジンは ML Kit（Capacitor のネイティブプラグイン）で、これは Android アプリ（APK）版でのみ動作します。** ただし `pnpm dev` やブラウザ版（GitHub Pages）では ML Kit のプラグインが存在しないため、読めなかったとき用に追加した PaddleOCR（WASM、[onnxruntime-web](https://onnxruntime.ai/)）へ自動で切り替わり、文字モードのシャッターボタンはそのまま押せます（初回だけ約35MBの読み込みが走り、ML Kitより低速です。詳細は前述の「3.5. 読めないとき用に PaddleOCR を追加」）。バーコードモードはブラウザでも従来通り動作します。
